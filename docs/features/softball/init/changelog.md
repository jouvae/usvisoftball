- 2026-07-09 — **🔐 SECURITY DEFECT found in the migration's grants (orchestrator; T3 surface).** The migration asserted `grant select on public.articles to anon, authenticated` and commented that this made it self-contained. `information_schema.role_table_grants` showed `anon` and `authenticated` actually holding **`DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE`** — Supabase's default privileges already grant ALL on new `public`-schema tables, so our `grant select` **added nothing and narrowed nothing**. RLS default-deny covers `INSERT`/`UPDATE`/`DELETE`, but **PostgreSQL row security does not apply to `TRUNCATE`**, which is gated *solely* by the table privilege — and `anon` is the publishable key, which ships inside the browser bundle. **Not remotely exploitable today** (PostgREST exposes no `TRUNCATE` verb), and stated as such rather than inflated. Fixed by `revoke all … from anon, authenticated;` before the `grant select`, so the table's real privileges match the model the migration documents. **Corrected the mental model project-wide: grants bound what is reachable at all; RLS bounds which rows. Both are load-bearing.** Lesson: a migration that *runs* is not a migration that *does what its comments claim* — read the catalog, not the script.
